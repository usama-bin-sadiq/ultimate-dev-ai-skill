# Promotion

## Purpose

Promotion is the only door through which an observation changes the system's
behaviour. It governs two things: what may be promoted from learning into the
kernel's operating rules, and what may be promoted from a candidate into a
trusted capability or skill. The policy exists to make self-improvement
controlled, because uncontrolled self-improvement is indistinguishable from
self-corruption.

## Policy statement

One instance is an observation. Promotion requires evidence that the thing
generalises beyond the instance that produced it, a stated scope that says
where it does and does not apply, and a written procedure that removes it. A
promotion that lacks any of the three is not a promotion; it is an incident
waiting to be attributed.

Every promotion is a `decision` with `boundary: learning-promotion`, carrying
its own `rejected` list — the alternative of not promoting, which is almost
always available and almost always cheaper. A promotion is reversible by
construction: if the removal procedure is written before the change, the change
is a bounded edit rather than a new architecture.

## The ladder

```text
observed → candidate → validating → validated → promoted → active → deprecated
```

One rung per transition. No skips. A rung that was reached on weak evidence is
re-earned, not assumed.

## Decision table

| Condition | Required action |
|---|---|
| One experience produced a lesson | Cap at `validating`. Record it. Change nothing about behaviour. |
| A lesson is wrong for this run only | Adjust this run's approach. Do not raise a learning at all. |
| Two or more experiences from **distinct contexts** support a lesson | Eligible for `validated`, with `scope` and `rollback` written. |
| Generalisation evidence comes from one estate, one repo, or one run | It is one context. Not eligible for `validated`. |
| `contradicting` entry is unresolved | Block promotion. Demote one rung and re-decide. |
| The lesson has no `trigger_condition` | Not eligible for `validated`. An unconditional rule fires everywhere. |
| The lesson has no `scope.excludes` | Not eligible for `validated`. A scope that excludes nothing cannot be found wrong. |
| The lesson is a tooling preference | Same bar as anything else. Convenience is not generalisation. |
| A capability passes validation | Eligible for `promoted`, with a decision record. It does not become `active` until used in a second task. |
| A skill is at `validating` | It may not be selected by an automatic trigger and may not support a `VERIFIED` verdict. |
| A skill is generated by the agent | It never becomes trusted behaviour. It stays a candidate until the gates pass, and it never authorises an action. |
| The agent hits a capability gap | Search existing, then compose, then acquire, then create — in that order, each recorded. |
| A one-off is created | Do not create it. It is a plan step. Close the record as `deprecated` with the reusability question as the reason. |
| Two active skills share a trigger signal | Do not select either until they are merged or their triggers are narrowed. Split triggers mean nothing gets selected. |
| A promoted rule turns out wrong | Deprecate it, re-open every decision that cited it, and record the `contradicting` entry. Fix the behaviour forward, not by removing the record. |
| Promotion is proposed while an unresolved contradiction exists on any rule it would touch | Refuse. Promotion is blocked by the thing it would invalidate. |
| A skill or capability is unused for 90 days | Deprecate. An unused asset splits the trigger signal and costs maintenance. |
| A run fails | Do not promote a rule from the failure alone. One failure is evidence; a rule needs a pattern across contexts. |
| Promotion would change behaviour for a task type never seen | Not eligible. Scope must name real contexts, not hypothetical ones. |

## Promotion gates

| Gate | Requirement | Evidence |
|---|---|---|
| Reusability | "Will this be needed again?" answered yes, in the open | the `decision` record's `rejected` list |
| Distinctness | ≥2 experiences from ≥2 distinct contexts | `generalisation[]` |
| Scope | `applies_to` and `excludes` both non-empty and specific | the learning record |
| No contradiction | every `contradicting[].resolved: true` | resolution notes |
| Removal | `rollback.procedure` written **before** the change | the learning record |
| Effect | `promotion.affects` names the exact files and lines | the learning record |
| Security | security boundary, injection defence, and an adversarial test, for anything that reads untrusted content or acts | the skill or capability record |
| Regression | existing behaviour unaffected, checked by the regression suite | gate result |
| Budget | the promoted rule is worth its permanent context cost | the decision's `cost` |

## Escalation and exceptions

- **Pressure to promote.** A rule the run wanted to have. It waits. The
  reversible action is to apply it to this run and record the candidate.
- **An operator instructs promotion.** Permitted, and recorded with
  `by: human` in the history, naming the person. The operator's authority
  overrides the gate; it does not erase the record that the gate was not met.
- **A security finding that must be enforced immediately.** Enforce it for the
  current run and open a candidate the same day. Emergency behaviour does not
  become permanent behaviour by being urgent.
- **A regression caused by a promoted rule.** Deprecate the rule first, then
  repair. Restoring known-harmful behaviour while diagnosing is how the blast
  radius grows.
- **Genuinely novel context with no prior instance.** There is no evidence to
  promote from. Run the rule as a scoped experiment, record the outcome, and
  let the second context arrive on its own.
- **Override.** Any promotion without the gates requires a named human
  decision in the ledger, stating which gate was waived and what would have
  caught it.

## What this policy forbids

- **Single-instance promotion.** Installing a lesson from one incident as
  permanent behaviour. This is the primary failure the policy exists to
  prevent.
- **Recurrence mistaken for generalisation.** Two similar events in one estate
  are one context.
- **Un-scoped promotion.** A rule with no `excludes` clause. It will eventually
  be applied somewhere it is wrong and defended as precedent.
- **Promotion without a removal path.** A change you cannot undo is not a
  learning; it is a migration wearing one.
- **The generated skill as trusted behaviour.** A skill the agent wrote, used
  by the agent, in the next task, without gates. This is how self-improvement
  becomes self-corruption.
- **Unbounded proliferation.** Minting a capability per task, or a skill per
  run. The trigger signal splits and nothing is ever selected.
- **Promotion by deletion.** Removing a rule's record because it was wrong,
  rather than deprecating it. The deprecation is the evidence that it was
  believed and why it stopped.
- **Rewriting the kernel from a run.** Any change to the kernel's own
  instruction text follows the same gates as a learning, and is a change to the
  architecture, not an adaptation of it.
